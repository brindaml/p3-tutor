Context and memory: what your assistant can see, keep and find

By the end of this lesson you can take one makerspace request and say what goes into the model's context, what the program keeps between steps, what it saves between sessions, and how it finds the right manual page.

Objective O3: context and memory in an agent About 30 minutes, including practice One-page cheat sheet
Why this matters for you

Your mission includes deciding what the assistant keeps in its context, what it saves between sessions, and how it finds a page in a long manual. These choices affect answer quality and your sponsor's model budget. This lesson gives you the words and the reasoning to defend them at design review.

The context window: everything the model can see 4 min

Start with an example. Picture a small workbench. To do a job, you can use only what is on the bench: the instructions, your tools list, the page you opened, your scribbles. A shelf across the room does not help until someone brings something over.

For a model, the bench is its context: the set of tokens it is given when it generates a reply (Anthropic, context engineering). A token is a small chunk of text, such as a short word or a piece of a longer word. Models read and write in tokens, so we measure text in them.

The context window is all the text the model can reference while generating a response, including the response itself. It has a maximum size in tokens, which depends on the model (context window docs). Those docs are one provider's, but they make a useful concrete reference.

In an agent, much more than the student's question takes up room. According to the same docs, all of these count:

  • the system prompt, which is your standing instructions to the model;
  • the tool definitions, which describe each tool the model may ask for;
  • every message so far, including the model's earlier replies and requests;
  • every tool result, plus any documents or images you send;
  • the output being generated now.

What if you send too much? In the docs above, if the input alone is larger than the window, the API (the interface your Python code calls) rejects the request with an error. A reply that reaches the limit while being written can be cut off.

Staying under the limit is not enough. As the token count grows, accuracy and recall can degrade. This is called context rot (docs). So treat context as a limited resource. The aim is the smallest set of useful, relevant tokens that gets the result you want (Anthropic). Smallest does not always mean short: leave in what the model needs.

Cost matters too. Model inputs and outputs are measured in tokens, and usage is billed by them. Even when one service links calls for you, earlier input in the chain is billed again as input (conversation state guide). Providers may discount repeated text through prompt caching, but cached text still takes up room in the window (docs).

Check yourself

Your team adds eight new tools, each with a long description. No student has used them yet. What happens to the context?

Show the answer

"Each call carrying them has less free room." Tool definitions count even if the tool is never used.

Between steps: the program keeps the history 6 min

Example. Imagine a helpful expert with no memory of earlier phone calls. Each time you call, you read them the whole case file so far. They suggest the next step and hang up. You keep the file.

Your program is in your position. The API guide I am using says its Messages API is stateless: you always send the full conversation history with each request (API primer). Stateless means one call does not rely on the service remembering your last one.

Some services offer to store the history for you. The same primer describes a beta feature that does this, with an expiry time. That changes who holds the list. The model still works from the history supplied to that call, and that history still takes up context. The other guide above notes that earlier input in a linked chain is still billed. In this course, assume your program keeps the history unless you have chosen such a feature.

So what is kept between steps of one task? Usually a list in your program. Here is a simplified sketch. It is not any real library: call_model and run_tool are stand-ins.

messages = [question]
for step in range(MAX_STEPS):
    reply = call_model(system_prompt, tools, messages)
    messages.append(reply)          # keep what the model said
    if reply.is_final:
        break
    result = run_tool(reply.request)  # your program runs it
    messages.append(result)         # keep what came back

Notice both append lines. The model's request and the tool's result both join the list. On the next call, the model reads the list and can tell what was asked, what it already tried and what came back.

The list lives in your program. The model sees it only when your program sends it. And the model only requests a tool; your program runs it.

Worked example: counting the tokens

A student asks, "Is the laser cutter free Friday, and what does its manual say about cutting acrylic?" All sizes below are made up to keep the arithmetic easy.

PieceTokens
System prompt600
Tool definitions400
Student's question50
Each tool request from the model50
Calendar result200
Manual search result2,000
Final answer150
Worked example
  1. Call 1 input: prompt, tools and question: 600 + 400 + 50 = 1,050. The model asks for the calendar.
  2. Call 2 input: everything from call 1, plus that request and the calendar result: 1,050 + 50 + 200 = 1,300. The model asks to search the manual.
  3. Call 3 input: everything so far, plus the new request and manual text: 1,300 + 50 + 2,000 = 3,350. The model writes the 150-token answer.
  4. Total input sent: 1,050 + 1,300 + 3,350 = 5,700 tokens.
  5. Fullest point of the window: call 3, with 3,350 input + 150 output = 3,500 tokens.

Keep those last two numbers apart. The window limit applies to what one call holds. Your usage adds up across calls. A task can fit comfortably in the window and still send many tokens in total. This example ignores caching discounts and any extra reasoning tokens a model might produce.

A common mix-up

"The model runs the tools and remembers what it did, all inside one go." It is tempting because a chat app shows one smooth reply. Underneath, the worked example has three separate model calls. Between them, your program runs the tools and extends the list. If the program dropped the calendar result, the next call would have no copy of it.

Check yourself

Suppose the example task needs a fourth call, because the student's training record must be checked after the manual search. If nothing is removed, what happens to the 2,000-token manual text?

Show the answer

It is sent again on call four. Reading something once does not store it in the model.

Between sessions: only what you save and load 5 min

Example. A clinic receptionist writes details in your file. At your next visit, someone pulls the file and reads it. Writing it down and pulling it out are two separate jobs. Both must happen.

Here, a session means one continuous conversation or task, such as one student's visit to the assistant. When a new session starts, your program decides what goes into the new context. For something from last week to be used, your system needs to do three things:

  1. Save it somewhere that lasts, such as a file or a database.
  2. Fetch the right item later, for the right student.
  3. Load it into the model's context.

Information stored outside the context window and pulled back in later is what people usually mean by an agent's long-term memory (Anthropic, structured note-taking). It can be very simple. A file counts.

The program can load a memory at the start of a session. Or it can give the model a tool, such as a lookup, so the model can ask for it when needed. A saving tool works the same way: the model requests a save, and your program does the writing.

What should you save?

The rules in this table are design suggestions for your assistant, not a standard.

InformationSensible handlingReason
Training statusRead from the official training record when neededIt controls safety, and it can change. A remembered chat claim is not proof.
Calendar availabilityCheck the calendar freshAn old "free" may now be booked.
A student's project and preferencesSave a short note, if the student is fine with thatUseful later and not held elsewhere.
Full old transcriptsDo not load them by defaultMostly irrelevant tokens, and possibly private ones.

For each saved item, ask four questions. Who may write it? Who may read it? When does it expire? How can a wrong entry be fixed? A mistaken note that gets loaded every visit can cause the same mistake every visit.

A common mix-up

"The assistant will automatically remember earlier conversations, including which tool worked last time." It is tempting because some chat products appear to remember you. A product can do that by saving information and supplying it again later. Do not expect it from a model call by itself. In your design, if nothing saves it and nothing loads it, a new session does not have it. What the model learned in training is a separate thing: saving a note adds nothing to that training.

Check yourself

Last week a student told the assistant their project uses plywood. Your program logs all chats to a database. This week's new session does not know about the plywood. What is the most likely gap?

Show the answer

Nothing fetches the fact into the new context. A log that is never read back does not act as memory.

Long tasks: notes and compaction 4 min

Example. During a long lab, your bench fills with printouts. You write the key readings in your notebook, then clear the printouts away. You can keep working, as long as the notebook has what matters.

An agent can do something similar. In structured note-taking, it regularly writes notes to storage outside the context window, and those notes are pulled back in later (Anthropic). A to-do list or a notes file is enough. Here is an invented note for a troubleshooting session:

{
  "machine": "3D printer 2",
  "symptom": "first layer will not stick",
  "tried": ["cleaned the bed", "re-leveled the bed"],
  "next": "check the temperature setting in the manual"
}

These notes help in two places. Within a long task, they carry progress past a context reset. Across sessions, saved notes can let Friday continue Monday's work. In both cases, a note helps the model only once it is back in the context.

Compaction is a related move. When a conversation nears the window limit, it is summarized, and a new context starts from that summary (Anthropic). The article's coding example keeps important decisions, unsolved bugs and implementation details. It drops repeated tool output.

The risk is real: if you cut too hard, you can lose a small detail that matters only later. A summary is shorter because it leaves things out. The article advises first making sure the summary captures everything relevant, then trimming the excess.

A lighter option is tool-result clearing: remove old, bulky raw results from deep in the history. For example, after the assistant has used a long calendar dump, your program might replace it with "Friday 2 to 3 pm was free when checked." If the fact might have changed, check again.

TechniqueWhat it doesMain thing to watch
NotesWrites selected facts outside the contextMissing, wrong or stale notes; notes never reloaded
CompactionReplaces a long history with a summaryLost details; making the summary may itself use model tokens
Tool-result clearingRemoves old raw tool outputRemoving something still needed

For short makerspace requests, you may need none of these. Start with the simplest design, then measure how large your real conversations get.

Retrieval: bring the right page to the bench 5 min

Example. To fix one fault, you do not read the whole machine manual. You use the index, open the right pages and read those.

Retrieval means finding relevant stored information and adding it to the context. It lets a manual act as outside knowledge for the assistant. The manual stays in storage; only selected pieces come to the bench.

Do you always need it? Not always. Anthropic's 2024 article suggests that a knowledge base under about 200,000 tokens, roughly 500 pages, can simply go in the prompt, with prompt caching to lower cost (contextual retrieval article). That is one company's rule of thumb. Using its rough ratio of 400 tokens per page, one 60-page manual is about 24,000 tokens. Twelve such manuals are about 288,000. For your small budget, compare the real cost and answer quality of both designs.

A common approach is retrieval-augmented generation, or RAG (same article):

  1. Prepare: split the manuals into chunks, usually no more than a few hundred tokens each, and index them for search.
  2. Search: for a question, find the highest-ranked chunks.
  3. Add: put those chunks into the model's input.
  4. Answer: the model writes its reply using them.

Two kinds of search

Keyword search matches words and exact strings. BM25 is a widely used method for ranking such matches. Embedding search, also called semantic search, compares meaning. It turns each chunk and each query into a list of numbers, an embedding, so that texts with related meanings can be matched.

Each has strengths. The article's example is the query "Error code TS-999". Embedding search might find general text about error codes but miss that exact code. Keyword search looks for the string itself (source). Meaning-based search can help when a student's wording differs from the manual's. A hybrid search uses both and merges the results.

Chunks can lose their labels

Suppose a chunk says only, "Set the speed to the lower value before starting." Which machine? Which material? Splitting the manual may have removed the heading that answered this. Keeping the machine name, section title and page number with each chunk is a practical fix. The article's version adds a short explanation of context to each chunk before indexing it, and reports fewer failed retrievals in its tests.

Retrieval can return the wrong chunk or miss the right one. Ask the assistant to name the manual and page, and tell it to say when the retrieved text does not answer the question. Check this with real test questions. A citation helps a person verify; it does not guarantee a correct answer.

When to fetch

Your program can search up front, before the first model call. Or the agent can use just-in-time retrieval: it holds light references, such as file names or links, and uses tools to load content when needed (Anthropic). For you, a search_manuals tool could work this way. The tradeoff is that exploring during the task is slower than using text fetched in advance, and an agent can waste context on dead ends. A hybrid loads a little up front and fetches the rest on demand.

Worked example and practice 3 min

Worked example: a memory plan

Request: "Can I book the vinyl cutter Friday at 2? Remind me how to load the roll." This is one possible design.

  1. Start with a small context: instructions, tool definitions, the question and the signed-in student's ID. These are needed from the first call.
  2. Fetch changing facts: check Friday's calendar and the official training record. Old chat notes are not good enough. The booking software itself should also enforce training and availability rules.
  3. Retrieve the manual part: search for loading instructions on the vinyl cutter. Return a few labeled chunks with page numbers, not the whole manual.
  4. Keep between steps: the program keeps each request and result in the message list. If booking succeeds, the confirmation goes in the list so the final answer can report it.
  5. Save between sessions: the booking belongs in the booking system. A short project note may be saved if useful and permitted. The retrieved manual text needs no personal copy.

Show a solution

Fetch: this student's note from last week, especially what was tried and what happened. Search printer 2's manual for adhesion help, using the student's words and manual terms such as "adhesion." Return labeled chunks.

Keep between steps: the lookup requests, the loaded note, the manual chunks, and any new facts the student reports.

Save for later: an updated, dated note: symptom, fixes tried, outcomes and next step. Mark untested suggestions as untested. If no old note exists, the assistant should say so and ask what was tried, not invent a history.

Check your plan: does every old fact have a way to be saved, fetched and loaded? Did you avoid loading every transcript and the whole manual library without a reason?

Summary 1 min

  • The context window holds what the model can reference in a call, including its output. It is limited, and more text can cost more and reduce accuracy.
  • Between steps, the history is kept and supplied again. In a stateless API, your program does this.
  • Between sessions, memory must be saved, fetched and loaded.
  • Notes, compaction and result clearing help manage long work. Each can lose or mislead if done badly.
  • Retrieval finds selected stored text and adds it to context. Keyword and meaning-based search catch different things.
