Context and memory: what your agent sees, keeps and looks up

By the end of this lesson you can draw up a memory plan for your makerspace assistant: what goes into each model call, what is saved between visits, and how it finds the right page in a manual.

Objective O3: context and memory in an agent About 30 minutes, including practice One-page cheat sheet
Why this matters for you

Your assistant has to answer from long machine manuals and know about each student across visits, on a small model budget. At your design review, someone may ask, "Why not just give it everything?" You will be able to answer with numbers.

Describe the agent loop in your own words. How does it end?

Check your answer

The model gets a goal and a set of tools. It asks for an action, the action is carried out, and the result goes back to the model. This repeats until the model gives a final answer or a limit is reached. Now we look closely at "goes back to the model."

1. The context window 5 min

Start with one request. A student types: "Is the laser cutter free Friday, and what material can't I cut on it?"

For the model to handle this well, your program has to send it much more than that sentence. It sends instructions such as "You help students at the makerspace." It sends a description of each tool. If this is a follow-up, it sends the earlier messages too.

All the text the model can use for one response is its context. The context window is the room available for it. One provider's documentation describes it as all the text the model can reference when generating a response, including the response itself.

Think of a workbench. The model can only work with what is on the bench. The bench has a fixed size, and the new thing you build on it needs room as well.

The size is measured in tokens. A token is a small chunk of text, often a word or part of a word. As a rough guide, one provider's glossary puts a token at about 3.5 English characters for its newer models. The exact figure varies between models, so treat any estimate as approximate.

Two new terms appear in the figure. The system prompt is the set of standing instructions your program gives the model. A tool definition is the text that tells the model a tool's name, what it does and what inputs it needs. You have not written one yet. For now, notice that it takes up tokens, even in a call where the tool goes unused.

According to the same documentation, the system prompt, all messages, tool results, images, documents, tool definitions and the new output all count. If the input alone is too big, that API rejects the request with an error. Other limits and behaviors depend on the model you use.

The window limits two things you care about. The first is fit: how much can be in one call. The second is related but separate: cost. Model APIs commonly charge per token, with prices for input and for output. Text that fits is not free.

A common mix-up

"If it fits in the window, put it in." It is tempting because the model then has every fact available. But you pay to send those tokens. Quality can suffer too: as the token count grows, accuracy and recall can degrade, which is called context rot. Imagine hunting for one drill setting on a bench buried under every manual you own. Aim for the smallest set of text that gives the model what it needs. Anthropic's engineering guide treats context as a limited resource.

Check yourself

Your assistant has ten tools. A student only says "Hi!" and no tool is used. Your program sends all ten definitions. Do they take up context?

Show the answer

Yes. Every definition sent is part of the input, whether or not the model uses the tool.

2. Between steps: the program keeps the history 5 min

Imagine phoning a help desk where a new person answers every time and remembers nothing. You keep a case file and read the whole file to them on each call. They can help only because you read it out.

A basic model API works like that. It is stateless: it does not carry your conversation from one call to the next. The documentation for one such API says you always send the full conversational history. Some services offer to store the history for you. Even then, the history has to be kept somewhere and supplied to the model. It does not live inside the model.

In your agent, one step is one turn around the loop: a model call, plus running any tool it asks for. Between steps, your program holds the history, usually as a list. After a tool runs, the program adds the model's request and the tool's result to that list. Then it calls the model again with the updated list.

Here is the idea in simplified Python. call_model and run_tool are stand-ins, not a real library.

messages = [{"role": "user", "content": question}]

for step in range(MAX_STEPS):
    reply = call_model(SYSTEM_PROMPT, TOOLS, messages)
    messages.append(reply)            # keep what it said
    if not reply.get("tool_request"):
        break                         # final answer
    result = run_tool(reply["tool_request"])
    messages.append({"role": "tool", "content": result})

Look at what changes on each pass: only messages grows. The system prompt and tools are sent again each time. The model's "memory" of step 1 during step 3 is simply that step 1 is still in the list.

This also means you decide what the model sees. If your program drops a result from the list, the next call cannot read it. If your program keeps it, you send it again.

The window must hold the largest single call, plus its output. Your bill reflects the sum over all calls. These are different numbers, so calculate both.

Some providers offer prompt caching, which lowers the price of re-reading repeated input. Writing to the cache can cost extra. Cached text still occupies the window. The arithmetic in this lesson assumes no caching.
Check yourself

At step 1 the calendar showed the cutter is free at 2 pm. A bug removes that result from the history before the next call, and nothing else records it. What can the model do at the next call?

Show the answer

It cannot read the result. Only what is supplied to the call (and general training) is available.

3. When the context gets crowded 4 min

A student spends an hour planning a project with your assistant. They ask twenty questions, and several searches each return pages of manual text. The history keeps growing. Cost per call rises, useful details get buried, and eventually the request may not fit.

Your program can manage this. Here are three basic moves.

MoveWhat it doesWhat you risk
TrimDrops old messages.Losing an early detail that still matters.
Clear tool resultsReplaces bulky old results with a short marker.Needing the full text again and having to fetch it.
CompactReplaces older history with a summary.The summary leaving out something important.

Compaction means summarizing a conversation that is nearing the window limit and carrying on from the summary. The same guide calls clearing tool results one of the safest, lightest forms of compaction. It also warns that compacting too aggressively can lose subtle but important context. LangChain's documentation likewise notes that stale information in a long history can distract a model.

Example. A 2,000-token manual search result has already been used to answer a question. Your program replaces it with this 30-token marker:

[Cleared: laser cutter manual, p. 12, banned materials.
 Search again if the exact wording is needed.]

That saves 1,970 input tokens on every later call in this session. Over ten more calls, that is 19,700 tokens. The marker says where the text came from, so the assistant can fetch it again.

A summary is lossy by design, so decide what must survive it. For your assistant, that might be the student's goal, the machine, any safety limits already raised, and which bookings were actually made. Test this: run a long chat, compact it, and check that those facts are still there.

Explain it

Early in a long chat, a student said, "My sheet is polycarbonate." Later, compaction produces: "Student is planning a laser project." Why is this a problem, and how would you change the compaction instructions?

Compare your answer

The material is gone, so later calls cannot check it against the manual's limits. Tell the summarizer to keep exact materials, machines, constraints and completed actions. Then test that they survive. You could also record such facts in a separate, structured part of the session's data that your program always includes.

4. Between sessions: notes as memory 5 min

On Monday a student says, "I prefer short, step-by-step answers." On Thursday they open a new chat. A session here means one conversation. Thursday's session starts with a new history. Unless your system saved Monday's preference and supplies it on Thursday, the model cannot use it.

A common mix-up

"The assistant will remember what students tell it." It is tempting because chat products can appear to remember you. In a system you build, memory is a feature someone has to provide: something saves the information, and something brings it back into context. Telling a stateless model "remember this" stores nothing by itself.

People often use two names. Short-term memory is the history within one conversation. Long-term memory is data kept across sessions, outside any single conversation. A saved chat that can be resumed is still that one conversation's history.

One simple form of long-term memory is notes: short records saved outside the context window and loaded when needed. Anthropic describes agents that regularly write notes to storage outside the window and read them back later, such as a to-do list or a notes file. It is like a lab notebook. The notebook helps only if you write in it and open it again.

Who writes the note, and when? One option is to save during the conversation, for example when the model asks to use a save_note tool and your program carries it out. Another is a separate background job that reviews the chat afterward. LangChain compares these two: a background job avoids adding delay to the live reply. It still needs its own schedule, and a model-based job has its own token cost.

What belongs in a note? Here are design rules I suggest for your assistant. They are engineering judgment, so debate them with your team.

  • Save things that will help later and are hard to get elsewhere, such as a stated preference or an unfinished project.
  • Read changing, official facts from their source. Training status belongs in the training records, and bookings in the calendar. Look them up with a tool when needed. A copy in a note can go stale. The assistant "remembers" a student's training status between visits because the official record persists.
  • Date each note and say where it came from, so old or wrong ones can be corrected or deleted.
  • Tie notes to a verified student ID in your code, and load only that student's notes. Agree on what you store and who can see it.
{"student_id": "s-104", "date": "2026-11-23",
 "source": "student said so in chat",
 "note": "Prefers short, step-by-step answers."}

5. Retrieval: finding the right page 5 min

When you need a torque setting, you do not reread the whole manual. You use the index, open the right page and read that part.

Retrieval does this for a model: find relevant material in storage and put it into the context. When a model then answers using retrieved text, this is often called retrieval-augmented generation, or RAG. It works like memory because information stays outside the window until it is needed. Retrieval can fetch manual passages, and it can also fetch saved notes.

A common setup has two stages. Prepare once (and again when manuals change): split each manual into passages called chunks and index them. Anthropic's description uses chunks of no more than a few hundred tokens. At question time: search the index and add the best few chunks to the context.

Two common ways to search are:

  • Keyword search matches words and phrases. It is useful for exact strings, such as a model number or an error code. BM25 is a widely used ranking method of this kind.
  • Semantic search looks for similar meaning. It commonly uses embeddings, which are lists of numbers that a separate model computes from text. Texts with related meanings get similar lists. You do not need the math.

Semantic search can miss crucial exact matches, so systems often combine both. This is hybrid search. A very basic version of keyword matching looks like this:

def score(question, chunk):
    q = set(question.lower().split())
    c = set(chunk["text"].lower().split())
    return len(q & c)   # number of shared words

best = sorted(chunks, key=lambda ch: score(question, ch),
              reverse=True)[:3]

This toy ignores punctuation and treats "the" as being as important as "acrylic". It also returns three chunks even if none is relevant. Use it to see the idea, not as your search engine.

A failure to watch for. A chunk says, "Maximum thickness: 6 mm." For which machine and which material? Splitting can strip away the surrounding context. Keep the manual name, section and page with each chunk. Anthropic's method also adds a short explanation to each chunk before indexing it, so search can use that information.

Retrieval can return the wrong passage or miss the right one. Have your assistant name the page it used. If the retrieved text does not answer a safety question, it should say so and send the student to staff. Test with real student questions for which you already know the correct page.

You do not have to load everything early or fetch everything late. An agent can keep a short list of manual titles and fetch details just in time. The guide also describes a hybrid: some material up front, the rest on demand. A short safety rule needed in every chat could go in the system prompt. For a small collection, including all of it can be reasonable. Anthropic's 2024 article suggested this below about 200,000 tokens, using prompt caching. That is one source's guidance from that time. Check your model's window, answer quality and your budget.

6. Worked example and practice 3 min

Worked example: search, or send the whole manual?

All sizes and prices here are made up for practice. System prompt plus tool definitions: 1,500 tokens. Question: 50. Each tool request: 50. Calendar result: 300. Manual search result: 2,000. Final answer: 200. Nothing is cleared or cached. Input costs $1 per million tokens.

  1. Call 1 input: 1,500 + 50 = 1,550. The model asks for the calendar.
  2. Call 2 input: 1,550 + 50 + 300 = 1,900. The earlier request and result are now history. The model asks to search the manual.
  3. Call 3 input: 1,900 + 50 + 2,000 = 3,950. The model writes the 200-token answer.
  4. Fit: the largest call needs 3,950 input plus 200 output, or 4,150 tokens.
  5. Billed input: 1,550 + 1,900 + 3,950 = 7,400. At the made-up price, 1,000 such questions cost $7.40 for input. Output is extra.
  6. Alternative: put a 40,000-token manual in every call and drop the search. Now there are two calls: 41,550, then 41,900. Total: 83,450, or $83.45 per 1,000 questions.

Conclusion: sending the whole manual saves one call, but uses about 11 times as much input. With these numbers, search is much cheaper. A real comparison also includes output, search costs, caching discounts and answer quality.

One more turn: if the student asks a 50-token follow-up and everything is kept, the next call starts at 3,950 + 200 + 50 = 4,200 input tokens.

Your turn 2: your memory plan

For each item, decide: always in context, session history, saved note, or fetch when needed. Give one reason each.

  2. The 3D printer manual.
  3. "I mean the second printer," said two messages ago.

Show a solution
  1. Always in context: short and relevant to every chat. A prompt rule alone cannot guarantee behavior, so enforce safety-critical permissions in code too.
  2. Fetch when needed: retrieve the relevant chunks, with page labels.
  3. Session history: it explains what "it" or "that one" means in this conversation. If history is compacted, keep this detail while it matters.
  4. Saved note: useful across visits. Load it at the start of that student's sessions.
  5. Fetch when needed: read the official training record, because status can change. Your booking code should check it too.

Summary 1 min

  • The context window is limited room, in tokens, shared by instructions, tools, history, results and output.
  • Between steps, history must be kept and supplied again. With a stateless API, your program does this. The largest call determines fit; all calls add to cost.
  • For crowded contexts, trim, clear or compact, and check what you lose.
  • Between sessions, information carries over only if it is stored and brought back.
  • Notes and retrieval keep information outside the window until needed. Official, changing facts come from their source.
