Context and memory: what your assistant can actually see

By the end of this lesson you can decide what your makerspace assistant should keep in its context, save for later, or look up when needed, and say why.

Objective O3: context and memory in an agentAbout 30 minutes, including practice
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. You also have a small model budget. All three depend on one design question: what goes into each model call?

The context window 4 min

Start with an example. A student types, “Can I cut this plywood on the laser cutter?” Your program does not send only that sentence. It also sends the assistant's rules, the descriptions of its tools, and any earlier messages. It might add a page from the manual too.

All of this is the context: what the model is given to work from. Anthropic's engineers describe it as the set of tokens included when sampling from the model, which means when it generates output (context engineering article).

A token is a small unit of text that a model works with. It can be a word, part of a word, a character, or even bytes (glossary). So a token count is not a word count. Models can split the same text differently. When you need a real number, use your provider's token counter or the usage figures returned with each reply.

The context window is the limited space for the text a model can work with at once. One provider's documentation describes it as all the text the model can reference when generating a response, including the response itself. It calls this the model's “working memory” (context windows documentation).

According to that page, the system prompt, all messages, tool results, images, documents, and tool definitions count. So does the reply. A system prompt is the standing set of instructions your program sends, such as “You help students at the makerspace.”

Think of a workbench with a fixed area. The drawings, the manual, your parts, and your assembly space all share it. A thick binder on the bench leaves less room for everything else.

How big is the window? It depends on the model. When this lesson was written, the page above listed windows of 200,000 and 1 million tokens for different models. Check the figure for whatever model your team picks.

What if you go over? It depends on the API and model. In that documentation, input that is too large by itself is rejected with an error. A reply that runs into the limit can be cut off. On some models, a request that asks for too much reply room is rejected before it starts (details). Don't assume anything will quietly make room. Plan for your program to manage the space.

A common mix-up

“The context window is everything the model knows.” It is tempting because both feel like the model's knowledge. But training is what the model learned before you called it. The window holds the text for the current work. Putting a new laser cutter rule in a prompt does not train the model on it. The rule is there for calls whose context includes it.

Between steps: the program carries the history 6 min

Here is something that surprises many new builders. The model API described in the documentation I used is stateless: it doesn't keep your conversation from one call to the next. To continue, you send the conversation history again (working with messages). An API is the interface your code calls, like the web API in your class project.

Some services can store history for you. Even then, ask what is being put in front of the model on each call. In this lesson, your own program keeps the history.

In Python terms, picture a list. Your program appends each new item and passes the list on the next call. This is a sketch, not a real library:

history = [question]
steps = 0
while steps < MAX_STEPS:
    reply = call_model(rules, tools, history)
    history.append(reply)
    if reply.is_final_answer:
        break
    result = run_tool(reply)   # your program runs it
    history.append(result)
    steps += 1
# if the limit was hit, report that the task is unfinished

Each time around the loop is a separate model call. The model can use a calendar result because your program put it into history and sent it. Remove that second append for the result, and the next call never receives what the calendar said. (A real API would also expect each tool request to get a matching result.)

So what is kept between steps? In this design, it is whatever your program keeps. What the model can use is the part your program sends. The history of one conversation is often called short-term memory. One agent framework scopes it to a single thread, meaning one conversation. Its saved state lets the thread be resumed later (memory overview). So “short-term” describes its scope, not a number of minutes.

Why this affects your budget

Worked example: counting one request

A student asks, “Is the laser cutter free Friday, and what plywood can it cut?” These sizes are made up to keep the arithmetic easy.

  • Rules and tool definitions: 1,500 tokens
  • Question: 50 tokens
  • Each tool request the model writes: 50 tokens
  • Calendar result: 300 tokens
  • Manual search result: 2,000 tokens
  • Final answer: 200 tokens
  1. Call 1 reads 1,500 + 50 = 1,550. The model asks for the calendar.
  2. Call 2 reads the earlier 1,550, plus the 50-token request, plus the 300-token result: 1,900. The model asks for a manual search.
  3. Call 3 reads 1,900 + 50 + 2,000 = 3,950. The model writes the answer.
  4. Total input: 1,550 + 1,900 + 3,950 = 7,400 tokens. Total output: 50 + 50 + 200 = 300.
  5. Space used by the end of call 3: 3,950 input + 200 output = 4,150.

Notice the two different questions. The window question is about one call: does this call fit? The usage question adds up every call. The 1,500 tokens of rules and tools were sent three times. Don't compare the 7,400 total with the window size.

Now the student asks a follow-up in the same chat. If you keep everything, the next call starts with those 4,150 tokens, then adds the new question. The documentation describes this build-up: messages accumulate in the window as a conversation advances (source).

Some providers offer prompt caching, which can change the price of repeated input. Cached text still takes up window space (source). So these totals count tokens, not dollars. Some models also produce “thinking” tokens, with their own carry-forward rules. This example leaves them out.
Your turn: fill in the steps

Rules and tools are 1,000 tokens, and the question is 100. The model writes one 50-token tool request, gets a 600-token result, then answers. First step: call 1 reads 1,000 + 100. What does call 2 read, and what is the total input?

Show a solution

Call 1 reads 1,100. Call 2 reads 1,100 + 50 + 600 = 1,750. Total input is 2,850. Call 2 reads more than the new result: it also reads the earlier input and the request.

When the context gets crowded 4 min

Picture a student who spends an hour troubleshooting a 3D printer with your assistant. Forty messages and many tool results pile up. Many old status readings no longer matter.

Running out of room is one problem. Quality is another. As the token count grows, the model's ability to accurately recall information from the context can drop. This is called context rot (engineering article). The article describes a gradual decline, not a sudden cliff. So aim for the right information, not the most.

Your program has several ways to tidy up:

MoveWhat it doesRisk
Clear old tool resultsDrops bulky results no longer neededYou may need one again
Trim old messagesRemoves earlier parts of the historyAn early detail disappears
CompactContinues from a summary of the historyThe summary misses something

Compaction means taking a conversation that is nearing the window limit, summarizing it, and starting a new context with that summary (source). The same article warns that overly aggressive compaction can lose details whose importance shows up later. It describes clearing old tool results as a light-touch form of compaction.

For the printer chat, a useful summary might say: “Prints lift at one corner. Bed cleaned and releveled. Problem remains. Next: check bed temperature.” It keeps actions and the open problem, and drops the raw readings.

Tidying has trade-offs. If a model writes the summary, that is extra model work to budget for. A short chat may never need it. Also, removing something from context is not the same as deleting it from your database. Your program can keep a full record and send only part of it.

Check yourself

A long chat is compacted. The summary leaves out the exact bed temperature tried earlier. No other copy is sent or looked up. What can you expect on the next call?

Show the answer

The second option. A missing detail can't be relied on. Put facts you must not lose somewhere your program can reliably reload.

Between sessions, and notes as memory 6 min

On Monday a student says, “I'm building a plywood enclosure for my sensor project.” On Thursday they open a new chat and ask, “What laser settings should I look up for my project?” For the assistant to know what “my project” is, something from Monday has to reach Thursday's context.

Long-term memory is information kept across separate conversations, or sessions (memory overview). In the design here, it lives outside the model, in storage your system controls.

A common mix-up

“The assistant will just remember its users.” It is tempting because some chat apps appear to remember you. When they do, the system around the model is supplying saved information. In your build, you have to design that: what gets saved, where, whose it is, and when it is loaded. Calling the same model again does not do this for you.

Notes the agent writes

Structured note-taking, also called agentic memory, means the agent regularly writes notes to storage outside the context window and pulls them back in later (engineering article). A to-do list or a NOTES.md file are examples from that article.

For your assistant, the model might request a save_note tool. Your program runs it and stores the text. Later, your program either loads the note at the start or offers a read_notes tool. Either way, the note helps only once its text is in the context.

Notes also help within a long task. If printer troubleshooting history is compacted or reset, a short “already tried” note can be read back. That helps the agent avoid repeating steps.

Not every saved fact belongs in a note

This part is my design advice for your project. Ask how much a fact matters, and which source can be trusted to keep it right.

InformationWhere it livesHow the model gets it
Training statusOfficial training recordsA tool looks it up for the signed-in student
BookingsBooking calendarA tool checks when needed
Projects and preferencesPer-student notesLoaded or searched when relevant
Old chat transcriptsA log, only if needed and allowedNot sent by default

So “remember training status” should mean: keep it reliably and look it up. A model-written note could misread “I'm getting trained Friday” as completed training. A copied note could also go stale if training expires or is withdrawn. Your booking code should enforce training rules too, rather than leaving that only to the model.

For notes, decide four things:

  • What to save: facts likely to help later, not every sentence.
  • Whose it is: tie it to the signed-in account, so one student's notes never load for another. Your program, not the model, should set that ID.
  • How old it is: store a date. Update or remove notes that stop being true.
  • Who can fix it: give students a way to see and correct what is stored. Check your university's privacy rules.
Check yourself

Last month's note says a student prefers PLA filament. Today they say, “I use PETG now.” What should the assistant do?

Show the answer

The third option. Use the new preference and update the dated note. A student's claim should not overwrite an official training record, though.

Retrieval: finding the right page 5 min

Suppose the laser cutter manual is 100,000 tokens, another made-up size. A student asks how to clean the lens. You could paste in the whole manual. In a three-call request that keeps it throughout, the manual alone adds 300,000 input tokens. Even when it fits the window, that is a lot of usage, and extra clutter can hurt recall.

A good librarian helps you find the useful pages instead of reading you the whole shelf. Retrieval means searching a store of information and bringing back relevant parts. Retrieval-augmented generation, or RAG, gives retrieved information to the model to help it write its answer (contextual retrieval article).

A chunk is a short piece of a document. The article above describes chunks of usually no more than a few hundred tokens. Treat that as a starting point to test, not a law.

Here are two common ways to search:

  • Keyword search matches words and phrases. BM25 is one scoring method for it. It is useful for exact strings such as identifiers (source).
  • Meaning-based search uses embeddings: lists of numbers that represent text so that meanings can be compared. The question and chunks are embedded with the same model, then close matches are found (Microsoft's guide). The aim is to match different wording, such as “the cut is faint” and a passage about “low output power.” Test whether your search really does.

Embedding search can miss an important exact match, so some systems combine the two (source). For a first version, you could try keyword search over well-labeled chunks. Then test it with the ways real students ask questions, and add meaning-based search if it misses too much.

Where retrieval goes wrong

Imagine a chunk that says only, “Replace it every 200 hours.” Replace what, on which machine? Splitting can strip away context a passage needs (source). Keep useful details with each chunk, such as the machine name, section title, and page. The article's technique adds a short explanation of each chunk's place in its document before indexing.

Search can also return a similar but wrong passage, or miss the right one. Retrieving something does not make it relevant or correct. Have the assistant name the page it used, and say when the passages don't answer the question. For safety questions, send students to makerspace staff when in doubt. These steps lower risk but don't guarantee a correct answer.

Who starts the search? Your program can search before calling the model. Or the model can request a search tool when needed. The second fits just-in-time retrieval: the agent keeps lightweight pointers, such as file paths or links, and loads data with tools while it works (source). This can keep unneeded text out. Exploring at run time can be slower than using data fetched ahead. In your simple loop, a model-requested search also needs another model call to use the result. You can mix approaches: always send a few essential rules, and look up the rest.

How does this relate to memory? Both can keep information outside the window and bring in selected parts. You can retrieve from manuals or from a large collection of saved notes. Retrieved text stays in later calls only if your program keeps sending it.

Check yourself

A student types an exact replacement part code from a label. The manual lists that code. If you can try only one search first, which should it be?

The second option. Keyword search is a good first choice for an exact code. Meaning-based search can help when students describe a problem in their own words.

Worked example and practice 2 min

Worked example: planning one request

A returning student asks, “Book me the laser cutter Friday at 2, and remind me how to focus it.”

  1. Send the basics: rules, tool definitions, and this request. The model needs them to act.
  2. Load relevant memory: use the signed-in account. An unrelated filament preference can stay out.
  3. Look up live records: check training status and calendar availability now, since both can change.
  4. Retrieve: get a few chunks on focusing this laser cutter, with page labels. Leave out the rest of the manual.
  5. Carry between steps: your program adds each tool request and result to the history it sends next.
  6. Save afterward: the booking tool writes the booking to the calendar. Save a note only if something useful for later came up. Manual text can be retrieved again, so it needn't become a student note.
Your turn

After 30 messages about a failing 3D print, a student says, “Let's continue next week.” Decide: (1) What do you save? (2) What do you not load by default? (3) What do you check fresh? (4) How do you find help in the manual? The first is started for you: “A dated note, tied to this account, containing …”

Show a solution
  1. The printer, the symptom, what was tried, what happened, and the next step.
  2. All 30 messages and old status readings. Load the short note instead. Keep a full log only if there is a reason and you are allowed to.
  3. Things that can change, such as availability, training status, and the printer's current state.
  4. Search by printer model and symptom, using exact matching for any error text. Bring back a few labeled chunks.

Check yours: could a new session continue from your note without the old chat? Did you avoid treating an old reading as current?

Defend it at design review

A teammate says, “Pick a model with a huge window. Then send every manual and old chat each time.” Reply in two or three sentences.

Show one good reply

“Even if it fits, repeating that input uses up our budget, and a crowded context can make recall worse. Old chats can add stale details, and sharing them across students could expose private information. Let's send what each request needs, look up the rest, and measure token use and answer quality on real questions.”

Summary 1 min

  • The context window is limited space shared by the model's input and reply.
  • Between steps, your program keeps the history and sends it again. Repeated input adds up.
  • A crowded context can hurt recall. Clearing, trimming, and compacting save space but can lose details.
  • Between sessions, store information outside the model and bring it back into context. Use official records for training status.
  • Retrieval brings in selected passages. It can fail, so label sources and test it.

Say it in your own words: without looking, tell a teammate why a call can fit in the window while the whole request still uses more tokens than you expected.
