Context and memory: what your assistant can actually see

By the end of this lesson you can decide, for each piece of information in your makerspace assistant, whether to send it with every call, save it between sessions or look it up when needed, and say why.

Objective O3: context and memory in an agentAbout 30 minutesOne-page cheat sheet
Why this matters for you

Your assistant has to answer from long machine manuals, remember things about students between visits (including where they stand on training) and stay within a small model budget. All three come down to one design question: what text does the model receive on each call? At your design review, you can answer that with numbers.

The context window 4 min

Start with an example. A capable helper works at your makerspace desk. They have one odd limit: they remember nothing about your desk from one request to the next. Each time, you hand them a folder. They read it, write one reply, and forget it.

If the laser cutter's rules are not in the folder, the helper has only their general knowledge. They might guess, and the guess might sound confident.

That folder is like the model's input. In general, context is the set of tokens the model works from when it produces output (Anthropic Engineering). A token is a small unit of text that a model processes, often smaller than a sentence and sometimes just part of a word. Different models can split the same page into different numbers of tokens (Claude glossary).

The context window is the limited room for those tokens. As one concrete case, Claude's documentation counts the system prompt, all the messages (including tool results, images and documents) and the tool definitions. The reply being written counts too (context window docs). A system prompt is the standing instructions your program supplies, such as "You help students at the makerspace."

So for your assistant, one call's window might hold:

  • your instructions to the assistant;
  • descriptions of tools, such as the calendar check and manual search;
  • the student's question and any earlier messages you include;
  • results that tools have returned;
  • the new output the model is writing.

The window has a maximum size, which depends on the model. In the Claude API, a request whose input alone is too long is rejected with an error. On its newer models, a reply that runs out of room stops early (docs). Other services may handle overflow differently, so check yours.

Fitting is not the same as working well

Picture a workbench. A bigger bench holds more parts. But burying the one screw you need under hundreds of others does not help you find it. Models have a related problem. As the token count grows, accuracy and recall can degrade. This is called context rot (docs). Anthropic's engineers describe a gradual slope rather than a sudden cliff. They advise treating context as a limited resource, and aiming for the smallest set of useful tokens that gets the job done (article). Smallest does not mean leaving out something the task needs.

A common mix-up: "With a big enough window, we can stop worrying"

This is tempting because a large window makes the "too long" error less likely. But it does not make extra text free or harmless. You still send those tokens, and unrelated text can make the useful part harder to use. Window size tells you what fits. It does not tell you what you should send.

Between steps: the history is sent again 4 min

A student asks, "Can I use the laser cutter Friday?" Your agent needs several model calls to answer. Call 1 asks for a calendar check. How does call 2 know what the question was?

Your program tells it again. It keeps a list: the question, the model's tool request and the tool's result. For call 2, it sends the instructions, tool definitions and that list. For call 3, it sends the longer list.

The general idea is that the model does not, by itself, carry your conversation into the next call. Claude's documentation says its Messages API is stateless: you send the full conversation history (Messages API guide). Some services can store history for you, and the same guide describes such a feature in beta. That changes who holds the list. It is still saved history being supplied for the next call, not the model learning your conversation.

This working history is often called short-term memory: it tracks the ongoing conversation within one session. LangChain, a library for building agents, ties it to one conversation "thread" (LangChain memory overview). Here, a session means one conversation, and a step means one turn around the agent loop.

In Claude's API, as you keep sending earlier turns, they accumulate in the window (docs). Your program can choose to shorten or remove old material. LangChain notes that a long history may not fit, and that many applications benefit from removing or forgetting stale information (overview).

A trace in Python terms

Think of a Python list that grows. This is simplified pseudocode, not a real library:

history = [question]
reply = call_model(instructions, tools, history)
history.append(reply)          # a tool request
result = run_tool(reply)       # your program runs it
history.append(result)
reply = call_model(instructions, tools, history)

A real agent puts the last four lines in a loop, with a way to stop. Here is the whole laser cutter run:

Call 1Instructions, tools, questionCalendar request, then its result
Call 2All of the aboveManual search request, then its result
Call 3All of the aboveFinal answer to the student

What size costs you 4 min

Model use is often billed by the token. Claude's pricing page, for example, prices input tokens and output tokens separately (pricing). In a per-token scheme, text you send on three calls is counted as input three times, though some of it may get a discount.

Worked example: one question, three calls

These sizes are invented for easy arithmetic. Instructions are 600 tokens, tool definitions 900 and the question 50. Each tool request is 40. The calendar result is 150, the manual search result is 2,000 and the final answer is 200. Ignore any extra formatting tokens.

  1. Call 1 input: 600 + 900 + 50 = 1,550.
  2. Call 2 input: all of call 1's input, plus the first request and its result: 1,550 + 40 + 150 = 1,740.
  3. Call 3 input: all of call 2's input, plus the second request and its result: 1,740 + 40 + 2,000 = 3,780.
  4. Totals: input is 1,550 + 1,740 + 3,780 = 7,070. Output is 40 + 40 + 200 = 280.

Keep two numbers apart. The largest window use is in call 3: 3,780 input plus 200 output, or 3,980. The total input is the sum over all calls, 7,070. The first tells you whether you fit. The totals of input and output drive cost.

Now suppose you also paste a 60,000-token manual into the instructions. For a rough comparison, keep every other number the same, including the search step. Each of the three calls grows by 60,000. Total input becomes 7,070 + 180,000 = 187,070 tokens, over 26 times as much.

At an invented price of 1 dollar per million input tokens, 1,000 such questions cost about 7 dollars of input with the smaller design, and about 187 dollars with the pasted manual. Output costs extra.

Some services offer prompt caching, which lets repeated input be reused at a different price. It can change this comparison a lot. In Claude's documentation, caching changes what you pay, but the tokens still count toward the window (docs). So estimate with your provider's real prices and rules.

Calculate

A different run takes two calls. Call 1 has 1,200 input tokens. The model's tool request is 30 tokens and the result is 500. Call 2 sends all of it. What is the total input across both calls?

Show the solution

Call 2 input is 1,200 + 30 + 500 = 1,730. Total input is 1,200 + 1,730 = 2,930. If you got 1,730, you found the biggest input but left out what you sent the first time.

Between sessions: save it, then supply it 4 min

On Monday, Sam tells the assistant, "I prefer short answers." Sam returns on Thursday in a new conversation. Will the assistant know?

In a system you build, only if something saved that fact on Monday and it gets into the context on Thursday. Long-term memory is information stored for use across sessions (LangChain). It might be a database row, a file or a set of notes. It sits outside the context window.

Think of a paper logbook at the desk. Writing in it keeps the information. It helps only when someone opens the right page and reads it.

Every memory feature needs answers to four design questions:

  1. Write: what is worth saving, and who or what saves it?
  2. Store: where does it go, and which student does it belong to?
  3. Read: does the program load it, or can the model request it with a tool?
  4. Update: what happens when it becomes wrong?

Writing can happen while the agent handles the request. That makes the memory available right away but can add delay. Or a background job can write it later, which may leave other conversations without the new information for a while (LangChain).

LangChain also borrows three labels: semantic memory for facts, episodic memory for past experiences or actions, and procedural memory for instructions on how to act (overview). These do not require three databases. They help you ask what kind of thing you are saving.

Training status: check the official record

Your assistant needs to know each student's training status on later visits. Here is a design recommendation. Pick one official training record, updated only by authorized people or systems. Have your program, or a tool such as check_training_record, look up the current status when needed. Do not rely on an old chat note saying "Sam is trained." Status could be added, expire or be withdrawn, and the copied note would not change with it. A student's claim in chat should not update the official record.

Also have your program choose whose data can be loaded, based on who is signed in. Do not leave that choice to the model. One student's private notes should never appear in another student's context.

A common mix-up: "It's an assistant, so it remembers past visits"

Chat products can make memory feel built in. When you build your own system, do not assume it. If Thursday's input holds neither Monday's conversation nor a saved note, and nothing fetches them, Monday's detail is unavailable. A product that does seem to remember needs some mechanism that keeps information and supplies it later.

Check yourself

Retrieval: finding the right page 5 min

A student asks, "What materials must I not cut on the laser cutter?" A good human helper does not reread every manual. They find the laser cutter's materials section and read that.

Retrieval means finding relevant stored information and bringing it into context. Retrieval-augmented generation (RAG) combines retrieval with a model's writing: documents from an outside source are passed into the context window (glossary). This is memory you look things up in. It does not require retraining the model. The retrieved page is more input.

A common setup works like this (Anthropic on retrieval):

  1. Split documents into chunks, small passages often no more than a few hundred tokens.
  2. Build an index, a structure your program can search.
  3. For each question, find the most relevant chunks.
  4. Add those chunks to the model's input.

Here are two ways to search. Keyword search matches words or phrases. It helps with exact text such as an error code; BM25 is one common way to rank these matches. Semantic search tries to match meaning. It uses embeddings, lists of numbers that encode the meaning of text. It might connect "what is unsafe to cut" with a passage headed "Prohibited materials," but it can miss an exact code. Systems can combine both (source).

For a first Python prototype, you could try simple keyword search over chunks. Test it on real student questions. Add semantic search if it misses questions worded differently from the manual. This is my suggested starting point, not a rule.

Where retrieval fails

Imagine a chunk that says only, "Never leave it running unattended." Which machine is "it"? Splitting can strip away what gave a passage its meaning. Anthropic's method, contextual retrieval, adds a short explanation to each chunk before indexing it (source). A simple step in the same spirit is to keep the machine name, manual title, section and page with each chunk.

Search can also return the wrong chunk or miss the right one. Then the model writes from poor input. When you test, print the retrieved chunks first. If the right rule is not there, fix the search before you polish the prompt. Have the assistant cite the manual page and say when the retrieved text does not answer the question. A citation helps someone check, but does not prove the answer is right.

Up front or on demand?

Your program could search before the first model call and include the results. Or you could give the model a search_manuals tool to use when needed. The second approach is just-in-time retrieval: the agent has pointers such as file paths, and tools to load data while it works. Exploring this way is slower than using data fetched in advance, and a poorly guided agent can waste context on dead ends. A hybrid fetches some data up front and lets the agent fetch more later (article).

Not every document set needs retrieval. Anthropic's 2024 retrieval article suggests that a knowledge base under 200,000 tokens, about 500 pages, can go whole into the prompt, using caching to reduce cost (source). That is one provider's advice at one time. Your window, accuracy tests and budget per question should decide.

Notes and compaction 3 min

Suppose a student spends 40 messages troubleshooting a failed print. You do not want to resend every long tool result forever. But you cannot lose "we already replaced the nozzle."

Structured note-taking means the agent regularly writes notes to storage outside the context window, and those notes are pulled back in later (article). The article's examples include a to-do list and a notes file. For your student, a note could be:

Goal: fix poor first layer on printer 2
Tried: cleaned bed; replaced nozzle
Result: problem remains
Next: check bed leveling (manual p. 14)

This note is invented. It can guide the next step. If it is saved under the right student and job, it can help in a later session too.

Compaction means summarizing a long context and starting a fresh one from that summary (article). A lighter step is clearing old tool results. The risk is losing a detail that matters later. Keep important facts, decisions and open problems, and test your summaries on long conversations.

TechniqueWhat it doesA main risk
RetrievalFinds relevant stored textWrong or missing passage
NotesSave facts or progress outside the windowWrong or outdated note
CompactionReplaces long context with a summaryLost detail

These can work together: a saved note can itself be retrieved. In each case, your system affects what text reaches a later call.

Worked example and practice 3 min

Worked example: place each piece of information

Ask three questions. Is it needed on this call? Must it last beyond the session? Does it change, or is it too large to send every time?

  1. Instructions on how to behave: needed on each call, so keep them short and send them each time. Real access rules, such as who may book, should also be enforced by program code.
  2. Machine manuals: long, and only parts matter for each question. Store and index them, then retrieve labeled chunks.
  3. Booking calendar: changes often. Check it with a tool. Last week's result does not show current availability. Even today's can go stale, so the booking step should check again.
  4. Answer-length preference: small, and useful across visits. Save it per student, load it at the start of a session, and let the student change it.
Your turn: the follow-up

Return to the three-call laser cutter example, without the pasted manual. In the same session, the student sends a 30-token follow-up: "What did that safety rule mean?" The model answers in one call.

(a) Your program keeps the whole history, including the 200-token final answer. How big is the new input? (b) Instead, it replaces the 2,000-token manual result with a 100-token note holding the key rule and page number. How big is the input now? (c) Name one risk of doing that. (d) The student returns next week. What must happen for the assistant to use that note?

First step: begin with call 3's input of 3,780. Try the rest before opening the solution.

Show a solution

(a) 3,780 + 200 + 30 = 4,010 tokens.

(b) 4,010 − 2,000 + 100 = 2,110 tokens, with nothing else changed. This leaves out any cost of creating the note.

(c) The note may drop an exception or distort the rule. For a safety question like this one, use the page reference to fetch the original wording again.

(d) The note must have been saved outside the session under the right student, then loaded or fetched into the new context. For a safety rule, also check whether the manual has changed.

Summary 1 min

  • The context window is limited room for what a call reads and writes. Fitting does not guarantee good results.
  • Between steps, your program or a history service keeps the history and supplies it again. Input adds up across calls.
  • Between sessions, information must be saved, then loaded or fetched.
  • Retrieval selects stored text, notes record facts and progress, and compaction shortens context. Each can fail.
  • For changing facts such as bookings and training status, check the official record.
