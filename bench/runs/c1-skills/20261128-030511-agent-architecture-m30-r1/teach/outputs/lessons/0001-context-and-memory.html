Context and memory: what your agent can actually see

By the end of this lesson you can decide, for each piece of information your makerspace assistant needs, whether it goes in the context, gets saved between sessions, or gets retrieved when needed.

Objective O3: context and memory in an agent About 30 minutes Keep nearby: one-page cheat sheet
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's situation between visits, on a small budget. You are the one who has to defend that design at your design reviews.

Warm-up 2 min

Answer from memory before you scroll. Both questions are about things you have already shown you understand, and today's lesson stands on them.

Recall 1

A model was trained before your makerspace bought a new 3D printer. Nothing about the printer is in its input. What can it reliably tell a student about that printer's local rules?

Show the answer

"Nothing, without being given them." Training plus input is all it has.

Recall 2

In the agent loop, the model asks to search the manuals. Who actually performs the search?

Show the answer

"The program around the model." The model requests; the program does.

The context window 4 min

Example

Picture a made-up Vanderpump Rules-style reunion. Invent two cast members, Dana and Marco, a host, and a producer named Priya. One twist: the host has total amnesia before every single question. The host still knows how to host, but remembers nothing about this taping.

So before each question, Priya hands over a binder. It holds 20 pages, and the host's reply has to be written in it too. Inside: the show rules, the list of clips Priya can roll, the questions and answers so far, and any clip transcripts. If Dana's season-finale comment isn't in the binder, then for this host it never happened.

The host is the model. The binder is the context window: all the text the model can reference when generating a response, including the response itself. The docs call it a "working memory". It is separate from what the model learned in training, which is the host knowing how to host.

The window is measured in tokens, the small units a model reads and writes. A token can be a whole word, part of a word, or a single character. For English, a rough planning figure is a few characters per token. It differs between models, so use a token-counting tool when you need an exact number.

What takes up space? Everything in the request, plus the output:

The limit is real. In the documentation I checked, input that is too long on its own is rejected with an error, and on newer models a reply that runs into the limit gets cut off with a stop reason saying so. Other services may behave differently, so check yours. Sizes also vary a lot by model, so look yours up.

Check yourself

Your assistant's instructions and tool descriptions are long, but the student's question is one line. Which of these uses space in the window?

Show the answer

"All of it, plus the reply." Even cached text still occupies the window.

Between steps: who carries the story? 5 min

Example

Question 1: the host asks Marco about the finale party. Marco answers. Then the amnesia hits. For Question 2, the host wants to say, "But you just told me you left early."

That only works if Priya added Marco's answer to the binder before handing it back. Priya also adds any clip she rolled. Each time, the host rereads the whole binder from page one, and the binder keeps getting thicker.

Many model APIs work like this. For example, one vendor's guide says its Messages API is stateless: you always send the full conversational history. Stateless means one call does not remember the previous call.

Some services can store the history for you (that same guide describes a beta option). That changes who holds the list. The model still only works from what is in its context for that call.

So your program keeps the memory between steps. It holds a list. After each model call it appends the model's output. After running a tool it appends the result. Then it sends the list again:

messages = [student_question]
while True:   # a real program also caps the steps
    reply = call_model(system, tools, messages)
    messages.append(reply)
    if reply is a final answer:
        break
    result = run_tool(reply)  # your code runs it
    messages.append(result)

This is pseudocode, so don't try to run it. Notice messages: it's an ordinary Python list, like ones you've used in class. That list is the short-term memory.

Why this hits your budget

Model usage is generally billed by tokens, and resending means you count the same text more than once. Here are made-up but realistic-sized numbers. The instructions, tools and question total 2,100 tokens. Step 1 adds a 100-token tool request and a 3,000-token manual result. Step 2 adds a 100-token request and a 200-token calendar result.

The final window holds 5,500 tokens, but you sent 12,800 input tokens. The 3,000-token manual result went in twice. Had there been more steps, it would keep riding along. Prices and caching discounts vary, and output is counted too, but the pattern is the thing to design around.

A common mix-up

"The model runs the tools and keeps track of what happened." It's tempting because a chat window looks like one continuous mind. In our reunion, the host never walks to the video room. The host asks; Priya rolls the clip and puts the transcript in the binder. If your program drops a tool result, the next call has no idea what came back.

Check yourself

A teammate's code appends the model's replies to messages but forgets to append tool results. What happens on the next call?

Show the answer

"The model cannot see that result." Your program is responsible for the history.

When the window gets crowded 4 min

Example

Two hours into the taping, the binder is at 18 of its 20 pages. Eight of them are a full transcript of one old clip about Dana and Marco's argument. Priya has to act.

She could pull those eight pages and leave a note: "Clip 3 shown; Marco admitted he sent the text." Or she could rewrite the whole first hour as a one-page recap. But if the recap leaves out when he sent it, the host can't use that detail unless someone goes back to the footage.

A bigger binder isn't automatically a better one. As the token count grows, accuracy and recall degrade, which the docs call context rot. Anthropic's engineers describe the same effect and argue for treating context as a limited resource to curate. So the goal is the useful information, not the most information.

Your program has a few moves:

MoveWhat it doesRisk
Clear old tool resultsRemoves bulky results that have already been usedYou may need to fetch one again
CompactionSummarizes a nearly full conversation and continues from the summaryA summary can drop a detail that matters later
TrimmingDrops the oldest messagesThe original goal or a key constraint can vanish

Compaction means summarizing a conversation that is nearing the limit and starting a fresh window with that summary. The same article calls clearing tool results one of the safest, lightest forms of it. Some platforms offer these features built in; otherwise your program does them.

Design tip for your review: say exactly what must survive any cleanup. For a booking assistant, I'd keep the student's goal, the machine, the requested time, and whether a booking was already made. Losing that last one could cause a double booking.

Check yourself

A long session holds a huge manual excerpt. The assistant already used it to answer, and the chat has moved on to booking times. What is the sensible first cleanup?

Show the answer

Clear the excerpt and note its source: a light cleanup you can undo by fetching again.

Between sessions: memory and notes 5 min

Example

The taping wraps. Months later, there's a new reunion. The host remembers nothing about the last one, and last time's binder is not on the desk.

But Priya kept a cast file in a cabinet: "Dana: said at last reunion she and Marco no longer speak." Before the new taping, Priya pulls Dana's page and slips it into the fresh binder. Now the host can follow up. A page left in the cabinet changes nothing.

When a session ends, the next one starts without that history unless your system puts something back. Long-term memory is information your system stores outside the context window and loads in later. It could be a file or a database row. It only affects the model once it is back in the context.

Notes as memory

In structured note-taking, the agent regularly writes notes that persist outside the context window and reads them back later. The article's examples include a to-do list, a notes file, and a model playing Pokémon that keeps track of its goals and maps across context resets. Notes help within one long task too, not only between visits.

One real design, a memory tool, shows the division of labor. The model requests actions such as viewing or editing memory files. Your application runs them and decides where the files live. A later conversation can use that memory if it has the tool and your app serves the same store.

A common mix-up

"The assistant will just remember each student." It's tempting because some chat products seem to. But a bare model call doesn't carry your last session forward. Any such feature is a system around the model that saves and reloads information. In your assistant, you have to design it. No cabinet and no producer means no callback to last season.

What to save, and what to look up fresh

My design recommendation: save what is helpful and has no better home. Look up live facts from their official source. A note can go stale, much like the outdated facts you've seen a chatbot state with confidence.

InformationWhere I'd get it
"Prefers short answers"Saved note for that student
"Working on a drone frame project"Saved note, with a date
Training statusOfficial training record, checked when needed
Machine availabilityBooking calendar, checked when needed

Your mission says the assistant must know each student's training status between visits. That means it has to persist, but the model doesn't need to be the thing storing it. If your makerspace has an official record, give the assistant a tool that reads it. If there is none, your team needs a database that trusted staff or code updates, not a model's free-form note.

Memory also brings your cybersecurity side into play. The memory tool docs advise checking every file path stays inside the memory directory, filtering sensitive data, limiting file size and expiring old files. I'd add: keep each student's memory separate, so one student's session can't load another's.

Check yourself

During a visit, a student says, "I passed laser training yesterday!" The official record doesn't show it. What should decide whether they can book the laser cutter?

Show the answer

The official record, checked right now. Safety permissions should not come from chat or notes.

Retrieval: finding the right page 5 min

Example

Priya's video room has hundreds of hours of footage. The host asks, "What did Marco say about the birthday toast?" Priya can't fit all the footage into a 20-page binder.

So she searches the episode logs, finds the two relevant scenes, and puts only those transcripts in the binder. If she grabs the wrong birthday, the host asks about the wrong fight, however good a host they are.

Retrieval means finding relevant information in an outside collection and placing it in the context. When a model answers using it, that's often called retrieval-augmented generation (RAG). It doesn't retrain the model. It changes what this call can read.

A common setup, as Anthropic's retrieval article describes it: split documents into small pieces called chunks, usually no more than a few hundred tokens. Prepare a searchable index ahead of time. When a question arrives, find the best chunks and add them to the prompt.

Two ways to search

MethodGood atCan struggle with
Keyword search (for example, BM25)Exact words, codes and identifiersA student using different words from the manual
Embedding searchSimilar meaning with different wordingExact codes or part numbers

An embedding is a list of numbers representing a piece of text, arranged so that texts with similar meanings tend to land close together. You can combine both searches and merge their results.

Chunking has a catch: a chunk can lose its surrounding context. Imagine one that says only, "Set power to 40%." For which machine and which material? Keep labels such as manual, machine, section and page with each chunk. The article goes further and adds a short explanation to each chunk before indexing it. In its tests, that approach plus matching keyword indexing cut top-20 retrieval failures by 49%. Treat that as its result, not a promise for your manuals.

When to fetch

You can search up front, before the model starts. Or you can use just-in-time retrieval: the agent holds lightweight pointers, such as file paths or links, and loads data with tools while it works. Exploring this way is slower than using precomputed results, and a poorly guided agent can waste context chasing dead ends. A hybrid does some of each. A search_manuals tool the model calls when needed is a just-in-time design, even if the index behind it was built earlier.

Must you use retrieval at all? Not always. The retrieval article says a knowledge base under about 200,000 tokens can simply go in the prompt, helped by caching. That's 2024 advice about what can work. On your budget, measure your manuals' size and compare cost and answer quality both ways.

Check yourself

A student asks, "Why does the cut edge look burnt?" The manual's section is titled "Charring and discoloration." Which search method is built to bridge that wording gap?

Show the answer

Embedding similarity search, because it matches on meaning.

Worked example and practice 3 min

Example

Final taping. Before asking Dana about Marco, Priya sorts the material. Show rules: in every binder. This taping's answers so far: in the binder, trimmed with care. Last reunion's key facts: from the cast file. A specific old scene: pulled from the video room. Whether Marco is on tonight's call sheet: checked on today's sheet, not on an old note.

Worked example

A student asks, "My acrylic keeps cracking on the CNC router. What should I change?" Suppose your 12 manuals average 30,000 tokens each. Instructions, tools and the question take 2,100 tokens.

  1. Size the naive plan. 12 × 30,000 = 360,000 manual tokens, so 362,100 input tokens on each call. It may not fit at all, depending on the model.
  2. Size a retrieval plan. Five chunks of 400 tokens add 2,000, so a call that includes them has about 4,100 input tokens, plus any other history.
  3. Pick a search. Students describe symptoms in their own words, while manuals contain exact model names and codes. Start with both embedding and keyword search, filtered to the router's manual.
  4. Add memory only where useful. A dated note, "uses 3 mm acrylic," can help. The assistant should confirm it's still true.
  5. Protect the session. Keep the goal, machine and advice already tried. Clear used chunks later, keeping page references.
  6. Test it. Write real student questions, mark the correct page for each, and check whether search returns it. Do this before blaming the model.

Your turn. First step done for you: the next week, the same student returns and says, "Book me the router Friday. Same material as last time." Last week's chat history is not loaded. A note says: "Nov 20: used 3 mm acrylic." Today you must work out the rest of the plan.

Your turn

Which plan handles this best?

Show a solution

Load the dated note into the new context. Ask, "Still 3 mm acrylic?" Check the training record and calendar with tools. Ask for a Friday time if one is missing, and book only when the checks pass. Retrieve manual chunks only if a setup or safety question needs them.

Summary and review lines 2 min

  • Context window: what the model can work from in a call. Input and output share a token limit.
  • Between steps: the history is carried forward, usually by your program resending it. This grows cost.
  • Crowding: clear used results, compact or trim with care, and protect key facts.
  • Between sessions: save outside the window, then load. Check changeable, high-stakes facts at their official source.
  • Retrieval: bring in the relevant pieces. If search misses the page, the model can't read it.

Say it in your own words: without scrolling up, explain to a teammate how your assistant can "remember" a student next week even though each model call starts only with what it is given. Name who saves, where, and how it gets back in.
